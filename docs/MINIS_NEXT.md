# Minis Next 1.5 / code 50

Version 1.5 completes App handoff for new CHROOT file_write output. The bridge supplies the real Process.myUid()/Os.getgid() and only the eight available App-managed session/global mount roots. The helper hands newly created files and missing parents to this identity through their open descriptors, before writing content. Existing targets keep their inode/owner/mode/ACL; external mounts and ordinary guest paths use normal Root creation rules. A failed handoff reports failure and never writes content to that new file. It does not recursively change historical files or shell-created directories. Tool results/logs now identify CHROOT euid/egid, target uid/gid/mode and the number of new objects handed off. The route is always CHROOT while selected: denied/unavailable Root never falls back to App writes. Rootfs initialization uses RootfsManager directly instead of booting PRoot and mirror detection. Cloud tests verify App read/overwrite after Root creates output in no-ACL 0755 and masked-ACL directories, plus new parent ownership. Android SELinux remains a separate device verification.


In CHROOT mode, text file_read/file_write/file_edit now execute inside CHROOT with the same Root identity, session mount table and tri-state Root gate as shell commands. This also handles pre-existing root-owned 0755 directories or 0600 files with no default ACL. Each operation under Ask requests its own approval; refusal/revocation stops it. Denied operations never fall back to another identity. Read-only mount and offload-placeholder guards remain before dispatch. Target ownership, mode, ACL and inode are preserved for in-place append/overwrite/edit. Root can access restrictive modes after approval, exactly as it does in the shell; permissions are not silently widened. Python3 from the bundled Ubuntu toolset is required. PRoot uses its previous App-UID implementation. Timeout/cancellation reports possible partial writes and does not retry automatically. Device CHROOT/SELinux still needs real-device validation.

The 1.3 update fixes App/CHROOT file handoff for newly created shared content. App-managed mount roots receive a default ACL for the actual App UID, with creation mode and later chmod still authoritative; root commands keep uid 0. No recursive ownership repair is performed. Fixed workspace/tmp is prepared by the App; existing restricted content and user mounts are preserved and diagnosed. Parent creation errors stop the write at the actual failure. See [the complete sharing policy, limitations and rollback](android-chroot.md#shared-file-handoff-in-13). Cloud host tests cover separate root/App file actors, not Android SELinux or a real device chroot.

The 1.2 update fixes the Android guest directory left over from the Alpine era. The live rootfs is now `filesDir/Ubuntu-rootfs` (capital U), extraction uses `filesDir/Ubuntu-rootfs.staging`, and a replaced guest is preserved as `filesDir/Ubuntu-rootfs.previous-<yyyyMMdd-HHmmss>[-n]`. On first launch an existing `filesDir/alpine-rootfs` is **renamed** to the new path — not copied, not re-extracted, and never unpacked over — so bytes, mtimes, installed packages and settings survive. PRoot `--link2symlink` `.l2s` records and older host-absolute references may still contain the old path, so an upgraded install additionally keeps exactly one relative compatibility alias `alpine-rootfs → Ubuntu-rootfs` (a symlink, never a data copy; all current readers use `Ubuntu-rootfs`). Fresh installs do not create the old name. A pending journal in `filesDir` makes an interruption between the rename and the alias recoverable on the next launch. If both directories contain data, both are left untouched and the conflict is surfaced as a visible error that blocks install and reset. Historical `alpine-rootfs.pre-ubuntu-*` backups and an old `alpine-rootfs.staging` remain discoverable through `RootfsManager.legacyBackupDirs` (the rootfs screen shows the latest preserved path) and are never auto-deleted.

The 1.1 interactive features are unchanged: native math plot drag/hit-testing and continuous sliders, the composer's original 20dp corners with 16dp bottom safe-area clearance, a per-provider custom HTTPS balance URL, and live model-catalog replacement with a visible error on failed refreshes.

Current branch: `minis-next`, repository https://github.com/liyongshun114514/Minis-Next . ## Provider settings (introduced in 1.1, unchanged in 1.2)

In the provider's Quota section, **Balance URL** accepts a complete HTTPS endpoint; blank restores automatic detection. The configured endpoint receives the instance's API key using Bearer authentication. Redirects are not followed. Common balance response shapes (DeepSeek, Moonshot, SiliconFlow, New API, Sub2API, billing, LiteLLM, Novita and root/data balance fields) are supported; unreadable responses are errors, never invented zero balances. An explicit ISO currency is kept; unknown sites do not get a guessed currency. Room v4→v5 adds one nullable column without deleting existing rows, and older backups default to automatic detection.

Each model refresh bypasses discovery caches. A successful catalog replaces upstream-discovered ids immediately, including an empty catalog; errors keep the previous list with a visible reason. Existing ids keep user overrides/hidden state. Hand-added custom rows and voice templates that are not supplied by the catalog are retained. No public catalog or compiled-in image list tops up a successful live answer. Removed ids are pruned from group and agent-loop references.

## Android guest directory in 1.2

- Canonical live tree: `filesDir/Ubuntu-rootfs`; staging: `filesDir/Ubuntu-rootfs.staging`; preserved previous guest: `filesDir/Ubuntu-rootfs.previous-<stamp>`. Constants live in `sandbox/SandboxDistribution.kt`.
- `sandbox/RootfsDirectoryMigration.kt` performs the one-time rename under a files-directory lock before any reader observes the path. It never copies, merges or traverses the guest; an empty legacy directory is the only thing removed.
- For upgraded installs it then creates exactly one relative symlink `alpine-rootfs → Ubuntu-rootfs`. This is a compatibility alias for PRoot `--link2symlink` `.l2s` records and older host-absolute references — not a second data tree. All current readers use `Ubuntu-rootfs`; a fresh install never creates `alpine-rootfs`.
- A journal at `filesDir/.ubuntu-rootfs-migration.pending` (exact content `Ubuntu-rootfs\n`) records the window between rename and alias creation. The next launch completes the alias if the process died there; an unrecognised journal, a missing target, or two non-empty directories aborts with a visible error and no overwrite.
- On disk, the string `alpine` is not guaranteed to be gone: an upgraded install has the alias, and historical `alpine-rootfs.pre-ubuntu-*` backups or an old `alpine-rootfs.staging` may exist. These are legacy **identifiers**, not the current distro label; `RootfsManager.legacyBackupDirs` reports the real backup trees (the alias is excluded).
- When both `alpine-rootfs` and `Ubuntu-rootfs` are non-empty, nothing is moved or deleted. `RootfsManager.rootfsMigrationError` is shown and both `installIfNeeded()` and `reset()` refuse to proceed.
- The old documentation claim that `alpine-rootfs` was deliberately kept as the live path is obsolete: no current reader uses it as the install destination.
- iOS/iSH remains Alpine; `deps/prepare_alpine_rootfs.sh`, historical measurements and legacy-compatibility fallbacks are intentionally not relabelled as Ubuntu.
